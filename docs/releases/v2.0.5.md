# Kaze 2.0.5

## Fixes

- Fix an indefinite buffering hang when a stream's decoder needs more audio than the initial download buffer. Downloading now continues independently while the decoder prepares playback.
- Keep Stop, Next, replacement playback and Quit responsive during stream preparation. Cancellation wakes waiting readers and finishes owned workers before shutdown waits for commands.
- Limit preparation to 30 seconds across source resolution, retries and initial decoding. Stalled or truncated downloads return a playback error so Retry and Next remain available.
- Prevent obsolete playback requests from publishing current-song events or deleting another request's partial file. Preserve completed caches, playback restoration, history and bookmarks.

## Verification

The fix passed 38 functional acceptance gates, including 265 Rust tests, 58 Node tests, both-interface browser checks and copied-binary native tests. In the controlled stalled-stream test, tray Quit exited normally in about 0.02 seconds after repeated play/Stop cycles in each interface. A short isolated native check streamed **House Of Balloons / Glass Table Girls — The Weeknd**, advanced playback, paused, sought, stopped and quit successfully. The user also confirmed playback now works without buffering.

The test-only loopback fixture feature is excluded from production builds. No database migration or frontend playback event-format change is required.

## Known limitations

The earlier suspend-related hang and long-session memory growth remain unproven/unresolved. These checks do not establish a full-song listening session or Windows/macOS runtime acceptance. Static-analysis findings remain documented in the audit; the scanner is not clean.
