# Streaming preparation and blocked Quit — 2026-11-03

The controlled HTTP regression confirms a preparation dependency deadlock in baseline source `b2433b4213823ff51391cb1e16a98bd7b2d4fc77`: synchronous Symphonia probing can consume the startup buffer and wait for more bytes, while the producer for those bytes is only spawned after probing returns. Preparation also was not registered with stream cancellation until after probing. The fixture required no suspend or hibernate. Whether the earlier sleep-related hang has the same cause remains unproven.

The user subsequently confirmed music now plays without buffering and authorized a new patch release, v2.0.5. Detailed evidence links below refer to locally retained diagnosis artifacts; raw thread captures and machine logs are not part of the public release commit. A compact acceptance summary is included.

## Evidence and provenance

[Evidence directory](2026-11-03-preparation-evidence/) retains both original thread-capture files, their hashes and original modification timestamps, the installed executable hash/build notes, sanitized log context, baseline failure, intermediate runs, and final acceptance records. Installed `/usr/bin/kaze` build ID: `0ab1dec8216a6e800d378098710c0550ce6ce6f9`. Source revision and binary identity are recorded separately: the captured executable is stripped, so its exact source correspondence and the addresses in the capture were not independently symbolicated. One capture is an unsuccessful ptrace attempt. The separate `/tmp/kaze-playback.log` records a GTK startup failure, not this preparation stall; its timestamp is retained without claiming it corroborates the hang.

The pre-fix subprocess uses the real `StreamPlaybackManager::try_start_progressive`, `ProgressiveStreamReader`, and `SymphoniaSource`, serving valid PCM WAV with a 256 KiB legal JUNK chunk before fmt/data. The server sends 64 KiB, waits 150 ms, and sends the rest. The unchanged code exceeded the external eight-second deadline even though the rest of the response was sent. [Baseline log](2026-11-03-preparation-evidence/before.log). Only the test child was killed by this deliberate regression deadline; actual application Quit uses graceful shutdown.

The initial fixture incorrectly wrote its response before reading the incoming request; reqwest rejected that exchange. Reading the request first produced the intended stall. Another harness issue appeared during concurrent builds: Cargo replaced the test executable before subsequent child launches. The regression now owns a temporary executable copy (on Linux copied from `/proc/self/exe`). These setup failures are distinct from the reproduced product bug.

## Implementation

- A `Preparation` owns a watch cancellation signal, progressive state, protected cache/unique partial paths, producer task and blocking probe task. It is registered before resolution or probing. Replacements cancel the old owner; the obsolete asynchronous download-slot cleanup/waiter mechanism was removed.
- The HTTP producer starts before the synchronous decoder. Probing and cached-file decoding run on blocking workers. The overall 30-second preparation timeout covers provider resolution, retries, and initial decoding. Existing 12-second connection and 25-second download inactivity limits remain; the separate successful-preparation restoration buffer retains its 120-second policy.
- Stop, Next, Previous, replacement and Quit signal cancellation and invalidate the generation before waiting on playback locks or command draining. Readers reject cancellation before buffered bytes, using a terminal BrokenPipe error (Interrupted can be retried by synchronous read helpers). Cancellation wakes the decoder, stops the producer, and joins workers; it does not abort a blocking task.
- Unique partial filenames prevent an obsolete request deleting a newer request's file. Creation and cleanup registration are synchronous together, avoiding late file creation after a cancelled asynchronous file-create future. Producer file handles close before partial deletion. Successful complete caches remain intact.
- Real response EOF and truncated/download errors reach readers. Terminal cancellation cannot be overwritten by a late completion/failure, and completion capability events require an attached playback session. Existing generation checks suppress obsolete playback publication; playback errors clear resolving state and preserve Retry/Next.
- Preparation and shutdown stages have concise diagnostics without signed media URLs. History/bookmark writes and SQLite shutdown remain graceful. There is no schema migration or frontend event-format change.

Product code: `src-tauri/src/playback/{stream,progressive,service}.rs`, shutdown stage diagnostics in `core/processor.rs`. Regressions: `stream_preparation_tests.rs`, `tests/progressive_stream_tests.rs`, and `scripts/test-preparation-tray.py`.

For a controlled native test only, `acceptance-fixtures` adds a startup option to preload a strictly HTTP/127.0.0.1 resolution-cache entry. This feature is absent from shipping builds. Build with `--features tauri/custom-protocol,acceptance-fixtures`, copy the executable, and run `KAZE_PRIVATE_TRAY_TEST=1 dbus-run-session -- python3 scripts/test-preparation-tray.py /absolute/path/to/copied-binary`. The harness uses private XDG directories and does not access the personal library.
